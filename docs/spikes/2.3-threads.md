# The assistant on a host that is not allowed every core

> Follow-up to [`2.3-inference.md`](2.3-inference.md), which measured *which
> model* on a machine with eight cores to itself. This measures what happens
> when the assistant is given a **budget** — four cores, six — because the
> deployment host also runs MariaDB, Redis, Reverb, a queue worker and the
> application, and llama.cpp will otherwise take every core it can see.
>
> Harness: `tools/spike/assistant/threads.sh` and `threads.mjs`. Re-runnable,
> which is the point.

---

## The finding that matters most, and it is not a latency number

**Job A and job C were returning nothing at all.** Not a slow answer, not a
poor answer — an empty string, on every run, on the model this project
recommends.

The sweep reported one output token for both jobs while job B generated
normally. That is the signature of a model emitting an immediate
end-of-sequence, so the prompts went in both ways for comparison:

| Job | `POST /completion` (what the application sends) | `POST /v1/chat/completions` |
|---|---|---|
| A — help answer | **1 token, `stop_type: eos`, empty string** | 88 tokens, a correct grounded answer |
| C — summary draft | **1 token, `stop_type: eos`, empty string** | 401 tokens, a correct summary |

The cause is a chat template. `gemma-3-4b-it` is an instruction-tuned model and
expects its turn markers; `/completion` takes a **raw** prompt and applies
none, so the model sees a finished document — one that ends "Reply with the
answer only." — and does the only sensible thing with a finished document,
which is to stop. `/v1/chat/completions` applies the template stored in the
GGUF's own metadata, and the same prompt then works.

Job B survived by luck. Its prompt ends `Reply with the JSON array only.`, and
a JSON array is a plausible *continuation* of that document, so the raw model
carries on. Asked the same way, a question about documentation is not.

**Why no test caught it.** Everything in `tests/Feature/Assistant/**` runs
against `ModelStub`, deliberately — a suite that reached a real 2.5 GB model
would be slow, non-deterministic and impossible in CI. But the stub replies to
whatever it is asked, so it cannot fail this way. And the 2.3 spike measured
through **Ollama's** `/api/generate`, which applies the model's template for
you; the runtime comparison that moved to llama.cpp exercised job B alone —
the one job that works raw. Three reasonable decisions, and the gap between
them was exactly the shape of this defect.

Fixed in W59, along with a contract test that runs against a real runtime when
one is configured and skips when there is not.

**After the fix, against a real model** (`vendor/bin/pest --filter=LiveRuntime`
with a runtime at eight cores): a help answer in **105s** cold and a suggestion
in **30s**, both non-empty and both correct.

**And prompt-prefix caching survives the move**, which matters because D21's
whole no-retrieval design rests on it. Two questions in a row against the same
corpus:

| | Wall | Prompt tokens | Served from cache |
|---|---|---|---|
| First question | 100.4s | 4,856 | 0 |
| Second question | **15.9s** | 4,860 | **4,819** |

The runtime caches on the token prefix regardless of which endpoint produced
it. The remaining 15.9s is mostly generation — 84 tokens at ~9.4 tok/s — not
prompt processing.

## The numbers

**Machine:** Intel i9-9900K, 8 physical cores, no GPU — the same workstation
as the original spike, so these are comparable with it and *conservative* for a
newer host. **Model:** `gemma-3-4b-it-Q4_K_M`, context 12,288.
**Method:** `docker run --cpus N` *and* `-t N` together, one container per
setting, started and stopped around each measurement.

| Cores / threads | Job A, cold prefix | Job A, warm prefix | Job B | Job C |
|---|---|---|---|---|
| **4** | 134.3s | 2.0s | **46.4s** | 199.3s |
| **6** | 98.2s | 1.4s | **35.9s** | 142.9s |
| **8** | 82.1s | 1.3s | **29.4s** | 114.1s |

Job A and job C are **prompt processing only** in these figures — they are the
runs that generated nothing, for the reason above. Adding generation at the
measured rate puts job C at roughly 250s on four cores and job A's first answer
at roughly 145s. Job B's figures are complete.

Resident size held at **3.26 GiB** at every setting, which is the number to
budget RAM against: the model file is 2.49 GB and the rest is the KV cache for
a 12,288-token context.

### The two rates scale very differently

| | 4 cores | 6 cores | 8 cores | 4 → 8 |
|---|---|---|---|---|
| Prompt processing | 36.1 tok/s | 49.5 tok/s | 59.2 tok/s | **1.64×** |
| Generation | 8.15 tok/s | 8.67 tok/s | 9.44 tok/s | **1.16×** |

**Generation is memory-bandwidth bound and barely cares how many cores it
gets.** Doubling the cores buys 16%. Prompt processing is compute-bound and
scales usefully, which is why the job dominated by reading a long fixed prompt
— job A's first question, job C — improves most.

Two consequences for an operator:

- **Giving the assistant more than about six cores buys very little.** The
  fourth core to the eighth adds 1.3 tok/s of generation. Those cores are worth
  more to MariaDB.
- **Setting `-t` higher than the cores the container may actually use makes it
  slower, not faster.** `ASSISTANT_THREADS` should be the number of cores you
  are willing to give it, and the container should be limited to the same
  number.

### Job B and the thirty-second line

Job B is a button with a spinner, and the 2.3 plan set 30 seconds as the point
past which that stops being reasonable. On this 2018 CPU it is **46s at four
cores, 36s at six, 29s at eight** — so on *this* machine a constrained
allocation crosses the line.

A newer host is faster per core: an i9-14900 P-core runs roughly 1.4–1.8× a
9900K core at this work, and its memory bandwidth is higher, which is the part
generation actually depends on. Four to six of those cores should land job B
somewhere in the mid-twenties to mid-thirties of seconds — around the line
rather than clearly past it.

**This is the reason W58 exists.** Rather than reshaping job B into a queued
flow on an estimate, every generation now shows elapsed time and can be
stopped. A 40-second wait a person can see and cancel is a different thing from
a 40-second wait they cannot.

## Re-running this on your own host

```bash
# 1. Fetch the model, and check the byte count — a truncated download exits 0.
mkdir -p ./data-spike-models
curl -L --fail --retry 5 --retry-all-errors -C - \
  "https://huggingface.co/ggml-org/gemma-3-4b-it-GGUF/resolve/main/gemma-3-4b-it-Q4_K_M.gguf" \
  -o ./data-spike-models/gemma-3-4b-it-Q4_K_M.gguf
stat -c%s ./data-spike-models/gemma-3-4b-it-Q4_K_M.gguf    # expect 2489757856

# 2. Sweep. About seven minutes per setting, dominated by job C.
MODEL="$PWD/data-spike-models/gemma-3-4b-it-Q4_K_M.gguf" \
  THREADS="4 6 8" tools/spike/assistant/threads.sh
```

Results land in `tools/spike/assistant/results/threads-*.json`, rewritten per
setting so an interrupted sweep keeps what it finished.

**What to look for, in order:**

1. **Does job B come in under 30 seconds** at the core count you intend to
   give it? If not, either give it more cores or accept that it is a
   forty-second action — which W58's progress and cancel make survivable.
2. **Is `outputTokens` a real number** for every job? A 1 there means the
   prompts are reaching the model without its chat template, which is the
   defect above.
3. **Resident size**, against what the host has spare. 3.3 GiB for the
   recommended model, and roughly 5.9 GiB for `qwen2.5:7b-instruct`.
