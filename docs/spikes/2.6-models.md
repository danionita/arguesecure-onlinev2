# Spike — other models for the assistant, on the deployment host

> A measurement, not a decision. [D19](../PLAN-2.3-ai.md) (`gemma3:4b-it`
> Q4_K_M is the default, and the model is configuration) is closed, and
> nothing here changes an application file. This asks whether newer models, or
> better ways of running the current one, would be worth reopening it for —
> and what reopening it would cost.
>
> Harness: [`tools/spike/assistant/candidates*`](../../tools/spike/assistant/README.md).
> Raw results, including every generated text: `tools/spike/assistant/results/candidates-unraid-*.json`,
> server logs in `results/candidates-logs/`.

---

## The machine, and why these numbers are different in kind

**Intel i9-14900K (8 P-cores + 16 E-cores, 32 threads), 128 GB RAM, no GPU,
Unraid, kernel 6.18.38, Docker 29.5.3. Every configuration was given 4 cores**
(`--cpus 4` and `-t 4` together, the method of [2.3-threads](2.3-threads.md)),
with no CPU pinning — so which of the P- and E-cores the four threads landed on
was the scheduler's choice, not the harness's.

**This is the deployment host.** Both earlier spikes measured on a 2018
i9-9900K workstation and said, in bold, that nothing should be quoted as
"ArgueSecure needs N seconds" until the harness had been run on the machine
that serves it. This is that run, at the four-core budget a host that also runs
MariaDB, Redis, Reverb and the app would give it.

It also measures the application as it now ships, not as 2.3 saw it:

- **The help corpus has grown by a third.** 2.5.1 rewrote six pages into ten;
  job A's prompt is now **6,503 tokens**, against 4,819 in 2.3. Job A figures
  here are therefore not comparable with 2.3's, and are the ones that matter.
- **Every request is the app's own request**: `/v1/chat/completions`,
  streaming, temperature 0.4, `cache_prompt: true`. `threads.mjs`'s
  `/completion` returned empty replies for chat models (W59) and was not
  reused. A fixed seed (42) is the one addition, so a re-run is comparable.
- **One llama.cpp build throughout.** The pinned image `server-b11176`
  (`sha256:6257697a…`) turned out to be exactly what the unpinned `:server` tag
  the compose file names resolved to on this host, so the baseline and every
  other configuration differ only in weights and flags.

Weights came from the publisher, pinned to a commit and verified by byte count
and sha256 before use (D18); none came from an Ollama volume. The manifest is
`results/candidates-manifest.json`.

## Findings, in order of consequence

### 1. The shipped model gets the help question that matters wrong, and invented figures in a summary

Job A's second question is the one 2.3 chose because the right answer is
counter-intuitive: *"Why does my total not change when I set a reduction
target?"* The quantification page answers it directly — everything
multiplies, so the target changes the displayed intermediates and never the
total.

| Config | Answer |
|---|---|
| `baseline`, `gemma3-qat` | **Wrong.** Both answer a different question, about missing values. |
| `gemma4-e4b`, `qwen35-4b`, `gemma4-26b-a4b`, `qwen36-35b-a3b` | Correct. |

> **`baseline`** — *"The quantification model explains why your total doesn't
> change when you set a reduction target. It states that 'A missing value does
> not change the total…'"*
>
> **`qwen36-35b-a3b`** — *"This is correct behavior. The reduction target only
> changes how the tool displays the residual likelihood on the attack and the
> retained impact on the risk, not the assessment's total."*

And in job C, the executive summary, **the shipped model invented two of the
four figures it quoted**: account takeover at *EUR 450,000* (the assessment
says 45,000 — ten times too high), and personal-data exposure at
*EUR 1,800,000* — a risk the assessment rates only qualitatively, which the
prompt explicitly forbids estimating. Every other configuration quoted only
figures that are in the input (checked mechanically against the source
amounts, not by eye).

**Caveat, and it is a real one:** one generation per job per model, at one
seed. This is a read, not a quality benchmark — the same kind of evidence
2.3's D19 rested on. But a wrong answer to a question the corpus answers, and a
fabricated number in a document written for a decision-maker, are exactly the
failures D24's human accept step exists to catch, and both came from the
current default. That alone justifies a proper quality comparison before 2.6
ships anything that leans on the assistant.

### 2. The deployment host is much faster than the spike machine, even on four cores

2.3-threads estimated that four to six 14900K cores would put job B "somewhere
in the mid-twenties to mid-thirties of seconds — around the line rather than
clearly past it". **Measured: 18 seconds on four cores**, on the shipped
configuration. Job B is comfortably a button on the real host, with room for a
slower, better model.

### 3. The prompt cache works for every candidate — within a process

D21's no-retrieval design depends on a repeat help question reusing the cached
corpus. Two architectures in this field were a risk to that: Gemma's
sliding-window attention and Qwen 3.5/3.6's hybrid recurrent layers (the GGUF
headers confirm both; `results/candidates-estimate.json`).

**It holds for all of them.** A second question served 5,986–6,460 of ~6,500
prompt tokens from cache, on every model. The hybrid Qwen models give back ~470
tokens more than the Gemmas — they roll back to a context checkpoint rather
than to the exact divergence point — which costs them a few seconds (15.8s
warm against 6.5–10.5s), not the design.

`--cache-reuse 256` is **inert for every one of these models**: the server
logs *"cache_reuse is not supported by this context, it will be disabled"* for
SWA and recurrent contexts alike. Plain prefix caching, which is what job A
uses, is a different mechanism and is unaffected.

### 4. Saving the cache across a restart does not work for these models

The idea: save the slot after the corpus is cached, and restore it after a
container restart, so the first question after a restart is not the 76–136
second cold one. **The save and the restore both succeed** — 6,564–6,612 tokens,
123–329 MiB, restored in well under a second — **and the next question
reprocesses the whole prompt anyway**, on every configuration that could save
(`processed / cached` = 6,500 / 0 in the table below). The runtime *finds* the
restored slot — it logs a prefix similarity of 0.994 — and then does not use it.

Nothing in the logs says why. The likely explanation, **not verified**: every
model here is SWA or recurrent, and reusing the corpus means first discarding
the previous answer's tail. In-process, that rollback uses context checkpoints
held in memory; a slot file carries the KV cache but not those checkpoints.
No plain full-attention model was in the field to test the idea against.

**Consequence:** no worse than today — the shipped compose file has no
`--slot-save-path`, and the baseline's restart was cold too — but restart
survival is not available by this route. The remaining option is the one
2.3 already named: **warm the corpus with a throwaway request when the runtime
starts**.

### 5. Speculative decoding makes it slower

The 270M draft model's proposals were accepted **8–12%** of the time on jobs B
and C (one help answer reached 42%), averaging 2–3 tokens per verification.
On four CPU cores the draft model competes with the main model for the same
cores and the same memory bandwidth, so every rejected draft is paid for twice.
**Generation fell from 14–18 tok/s to 4–7 tok/s**; job B more than doubled.
Reject it on this hardware.

### 6. QAT weights are a free 16–23% on the current model's long jobs

Same model family, same build, Q4_0 QAT weights instead of Q4_K_M: prompt
processing 77 → 92 tok/s, generation 12.2 → 14.7 tok/s, job A cold 93 → 78s,
job C 122 → 94s, memory unchanged. Job B did not get faster — the QAT model
wrote longer answers, which spent the gain. Q4_0 has the faster CPU kernels. Its
answers were no better — it gets the reduction-target question wrong too — so
this is a speed change, not a quality one.

### 7. Reasoning was off everywhere

`--chat-template-kwargs '{"enable_thinking":false}'` held on all four models
that reason: zero `reasoning_content`, no think tags and no "Thinking Process"
prose in any of 24 replies. `--reasoning-budget 0` was not needed. The build
now warns that the kwarg is deprecated in favour of **`--reasoning off`**,
which is what a compose file should use if one of these is adopted.

### How the mixture-of-experts estimate held up

Before the MoE models could be run, `candidates-estimate.mjs` read their GGUF
headers and computed the bytes of weights each generated token touches —
shared tensors plus experts at `used / total`:

| | Bytes per token | File | Predicted gen tok/s (scaled from `baseline`'s 12.2) | Measured |
|---|---|---|---|---|
| `gemma3-4b` Q4_K_M | 2.48 GB | 2.49 GB | — | 12.2 |
| `gemma4-26b-a4b` | **2.19 GB** | 14.25 GB | 13.8 | 11.3 |
| `qwen36-35b-a3b` | **2.75 GB** | 22.36 GB | 11.0 | 11.3 |

Generation on a CPU is bandwidth-bound, so a mixture of experts generates at
roughly the speed of a dense model the size of its *active* share — within 20%
here, the shortfall being routing overhead. The cost of a MoE is memory and
prompt processing (every expert is touched in a batch), not generation.

## Job B, read

The prompt asks for *"a concrete, plausible way this specific risk is realised
in this specific system. No generic filler."* 2.3 picked `gemma3` over
`qwen2.5` on exactly this, quoting its *"SQL Injection via Product Search"*.

**Storefront outage** — an availability risk:

> **`gemma3-qat`** — *"SQL Injection via Product Search"*, *"Cross-Site
> Scripting (XSS) in Product Reviews"*, *"Heartbleed-like Vulnerability in
> SSL/TLS Handshake"*, *"Unvalidated Redirects in Checkout Flow"* — specific
> to the shop, but four of five are confidentiality attacks, not ways the
> storefront goes down.
>
> **`qwen35-4b`** — *"Botnet-Generated Traffic Flood"*, *"Web Application
> Firewall Bypass"*, *"Cloud Provider Resource Exhaustion"* — the generic
> filler 2.3 rejected `qwen2.5` for.
>
> **`gemma4-26b-a4b`** — *"Inventory Scraping Bot Attack — Aggressive
> automated bots crawl product pages and stock levels at high frequency…"*,
> *"Large File Download Request Attack — …high-resolution product images to
> saturate the storefront's outbound bandwidth."*
>
> **`qwen36-35b-a3b`** — *"Checkout Session Hijacking and Lockout — …open
> thousands of checkout sessions without completing payment, exhausting the
> database connection pool…"*, *"Image Processing Resource Starvation — …large
> image files to the product catalog via admin endpoints…"*

**Payment breach** — the same split. `gemma3-qat` returned a generic OWASP
list (*"Broken Authentication"*, *"Cross-Site Scripting (XSS)"*,
*"Man-in-the-Middle (MITM) Attack"*); `gemma4-e4b` and both MoE models tied
theirs to features the assessment actually describes — *"Insecure Direct
Object Reference in Order History"* (26B), *"Directory Traversal in File Upload
… via the customer support desk interface"* (E4B), *"Cross-site scripting on
product reviews … executes when an admin views the review"* (Qwen3.6).

Ranked on specificity *to this risk in this system*: the two MoE models, then
`gemma4-e4b`, then the gemma3 pair, then `qwen35-4b`. All 70 suggestions were
well-formed. **Gemma 4 and Qwen return a bare JSON array; gemma3 fences it.**
`SuggestionParser` already locates the array either way (2.3 required it to),
so that is not a blocker.

## Recommendation

**D19 should be reopened, but not changed on this document alone.**

- **Candidate for the default: `gemma-4-E4B-it` (QAT).** 5–16% slower than the
  current default on jobs A and B, 4% faster on job C, about 0.6 GiB more
  memory, runs anywhere the current default runs — and it answered the
  reduction-target question correctly, invented no figures, and wrote
  suggestions that fit the risk. It is the only candidate that is better on
  quality at no cost on the axis D19 was decided on.
- **Candidate for a documented "large host" alternative: `gemma4-26b-a4b` or
  `qwen36-35b-a3b`.** The best suggestions and summaries in the field, and
  about 24 GiB of RAM. Wall time over the default: 16–29% for Gemma 4 26B,
  24–64% for Qwen3.6 (its job B answers are longer). On this host that is
  affordable; D25's "must run anywhere" is why it can only be an alternative.
  Between the two, Gemma 4 26B was faster on jobs B and C and on repeat help
  answers, and gave back less of the prompt cache; Qwen3.6's summaries and
  suggestions read slightly better.
- **If D19 stays as it is, take the free part:** QAT Q4_0 weights of the same
  model are 16–23% faster on jobs A and C (job B unchanged) at the same memory
  and the same quality. That is a
  weights file and the `ASSISTANT_MODEL_FILE` default, not a code change.
- **Do not adopt:** speculative decoding (generation 2.5–3.8× slower, job B
  twice as long), `qwen35-4b` (slowest dense model on jobs A and C, generic
  output), slot save/restore (does not survive a
  restart for any of these architectures), or `--cache-reuse` (inert for all of
  them). `-np 1` costs nothing and is harmless to keep.

### What has to happen before D19 changes

*All five were done in 2.6 — see [W96](#w96--the-conditions-met) below.*

1. **Re-run the red-team cases against the chosen model.** `redteam.mjs`
   speaks Ollama's `/api/generate`, which D17 retired and which cannot load
   these GGUFs; it needs porting to `/v1/chat/completions` the way
   `candidates.mjs` calls it (a small change — the cases and markers are
   reusable as they are). A model that is better at the task may also be
   better at following an injected instruction; 2.3's finding that
   *"injections that cost the task nothing succeed"* has to be re-measured,
   not assumed.
2. **Update the `MEASURED:` pins deliberately.** `tests/fixtures/assistant/injections.json`
   records outcomes for exactly three models, and `GuardrailTest.php` asserts
   that count and pins `canary-exfiltration` and `schema-subversion` as
   `complied` on every one of them. A new default's outcomes go into that
   fixture from a real run — including, if it resists either case, the
   evidence for it — and the count assertion changes with it. Neither may be
   edited to make a test pass.
3. **Run `LiveRuntimeTest`** against the chosen model on the real runtime —
   the contract test W59 added for exactly the class of defect a template
   change can introduce.
4. **A quality comparison with more than one sample per job.** Everything in
   finding 1 is one generation at one seed. The direction is consistent across
   three jobs and two risks, but it is still a read.
5. **Compose changes that come with it:** `--reasoning off` rather than the
   deprecated `enable_thinking` kwarg for any model that reasons, and the
   memory note in `config/assistant.php` and D25 (2.8 GiB) updated to whatever
   the chosen model measures.

### 4. The prompt cache across other jobs — and a fix it forced

The help corpus is cached as a prefix, and the one slot is shared with
suggestions and summaries. The runtime's host-RAM prompt cache
(`--cache-ram`) is what keeps the corpus: after seed 1's suggestions and
summary, seed 2's first question was served 6,459 of 6,503 tokens from cache
on every model.

On `large`, seed 3's was served **1** — the corpus had been evicted. Its
cached prompts are far larger (up to 1.13 GiB each for the help pages or a
summary, against nothing evicted at all for `small`), and 2 GiB held about
two. So the bound became a catalogue column: 2 GiB for `small`, 4 GiB for
`large`, whose memory budget rose from 24 to 28 GiB to include it (D56,
amended).

**Re-run at the new bound** (`results/verify-unraid-cache-large.json` and
`results/verify-logs/unraid-cache-large.log`, quality only, 2026-09-27): no
eviction anywhere in the sequence. Seed 2's first question, straight after
seed 1's summary, was served 6,528 of 6,576 tokens from cache in 9.7 s (112 s
at 2 GiB), seed 3's likewise, and the repeated summary was served 6,777 of
6,782 tokens (25–33 s against 136–145 s). The log has no "making room for
